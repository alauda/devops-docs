# Planning a Dedicated DevOps Cluster

Use this page to plan a dedicated cluster for the Alauda DevOps tools in an Alauda Container Platform (ACP) 4.5 delivery. It covers which tools to deliver, the node pools of the cluster, the minimum specification of each node, and the storage and middleware that the tools depend on.

The plan applies when the following conditions hold:

- The DevOps tools run in their own cluster, separate from the clusters that run business applications.
- The storage and middleware that the tools depend on are installed in the same DevOps cluster.
- No commercial storage is available, so the cluster runs its own Ceph distributed storage on dedicated storage nodes.

For the installation procedure of each tool, see [Installing Alauda DevOps next-gen](./installing-devops-next.mdx).

## Tools to Deliver

| Capability | Product | Operator in OperatorHub | Deployment form |
| --- | --- | --- | --- |
| Container image registry | Alauda Build of Harbor | `Alauda Build of Harbor` | High availability, with image layers on object storage: the layout of the `Harbor Object Storage` template, with at least 2 replicas of the portal, core, registry, and jobservice components. |
| Source code management | GitLab | `Alauda Toolchain Code Repository E1` | 2 replicas of the webservice, Sidekiq, and gitlab-shell components, and a single Gitaly (not Gitaly Cluster) on Ceph block storage. |
| CI/CD pipelines | Alauda DevOps Pipelines (Tekton) | `Alauda Container Platform Pipelines` | Operator-managed Tekton components. |
| Code quality | Alauda Build of SonarQube | `Alauda Build of SonarQube` | `Production Template`, single instance. |
| Artifact repository | Alauda Build of Nexus | `Alauda Build of Nexus` | `Production Template`, single instance. |

GitLab runs a single Gitaly. If the node that runs Gitaly fails, Git repository access is unavailable until the Gitaly pod runs again on another node. SonarQube and Nexus are single instances and behave the same way.

## Cluster Topology

The DevOps cluster has four node pools.

| Node pool | Nodes | Runs | Why this node count |
| --- | --- | --- | --- |
| control-plane | 3 | Kubernetes control plane and platform components | Three nodes keep etcd quorum when one node fails. |
| infra | 3 | Monitoring (VictoriaMetrics), logging (ClickHouse), and Ingress NGINX for this cluster | Same layout as the infra nodes of the workload clusters. |
| devops | 4 | The DevOps tools and their PostgreSQL and Redis instances | Each PostgreSQL instance and each set of Redis Sentinels runs 3 replicas, one per node, so the pool needs at least 3 nodes. The fourth node lets every pod reschedule when one node fails or is drained for maintenance. |
| storage | 3 | Ceph distributed storage: MON, MGR, OSD, and RGW | Three nodes, each with its own raw disk, is the Ceph minimum. |

Declare a role label on each pool, in the format `node-role.kubernetes.io/<role>`, and place the tool instances and the Ceph components with node selectors. On Alauda OS, declare labels and taints on the node-pool resources, not on individual nodes. See [Infra Nodes](https://docs.alauda.io/container_platform/4.5/configure/nodes/node_planning.html).

Harbor and GitLab high availability also require a highly available load balancer in front of Ingress. Reserve a virtual IP address (VIP) for the Ingress entry point of the DevOps cluster.

## Node Specifications

The values below are the **minimum recommended specification of each node**. Physical servers are usually larger.

| Node pool | Nodes | CPU | Memory | Data disk |
| --- | --- | --- | --- | --- |
| control-plane | 3 | 8 cores | 32 GiB | System and etcd disks as for any ACP 4.5 cluster |
| infra | 3 | 16 cores | 48 GiB | Local disk for monitoring and logging, as on the infra nodes of the workload clusters |
| devops | 4 | 32 cores | 64 GiB | None. All tool data is on Ceph |
| storage | 3 | 12 cores | 24 GiB | 1 × 2000 GiB enterprise SSD per node, raw and dedicated to Ceph |

Notes:

- The CPU and memory figures assume that requests equal limits for every component.
- On Huawei DCS, Huawei Cloud Stack, and VMware vSphere, the disk layout of a node pool cannot be changed after the cluster is created. Plan the disks of every pool before you create the cluster. See [Fixed at Creation](https://docs.alauda.io/container_platform/4.5/workload_clusters/alauda_os/#fixed-at-creation).
- The devops pool sizing covers the tools only. PipelineRun and TaskRun pods use additional capacity that depends on how many builds run at the same time. Add capacity for them separately.
- The storage nodes need 10 GbE or faster network interfaces for the Ceph public and cluster networks.

## Storage

All persistent data of the DevOps tools is stored on the Ceph distributed storage of the DevOps cluster. The plan uses Ceph block storage (RBD) and Ceph object storage (RGW). It does not use CephFS, so no MDS is deployed.

| Data | Storage | Notes |
| --- | --- | --- |
| PostgreSQL of Harbor, GitLab, and SonarQube | Ceph RBD | Do not place databases on CephFS. |
| Redis of Harbor and GitLab | Ceph RBD | RDB persistence enabled. |
| GitLab Gitaly (repositories) | Ceph RBD | The GitLab deployment page recommends block storage with read IOPS ≥ 8,000 and write IOPS ≥ 2,000 for production. Validate the Ceph RBD performance on the delivered hardware. |
| GitLab uploads (attachments, avatars) and LFS | Object storage: Ceph RGW, or the customer's S3-compatible storage | Only when the feature is used. Do not use a `ReadWriteMany` attachment volume. |
| SonarQube data directory | Ceph RBD | Do not use remote-mounted file storage for SonarQube data. |
| Nexus data (`/nexus-data`) | Ceph RBD | One volume for the single instance. |
| Harbor image layers (registry) | Object storage: Ceph RGW, or the customer's S3-compatible storage | |
| Harbor job logs | Harbor database | Set by the `Harbor Object Storage` template. |
| Harbor Trivy vulnerability database | `emptyDir` | The template default. After a Trivy pod restarts, scans pause until the database is loaded again. |

:::warning
Ceph requires at least 3 storage nodes, each with a dedicated raw disk. If the environment cannot provide them, this plan cannot be delivered.
:::

For Ceph deployment models and capacity rules, see [Planning Your Deployment](https://docs.alauda.io/container_platform/4.5/storage/storagesystem_ceph/planning.html).

## Middleware

Harbor, GitLab, and SonarQube each use their own PostgreSQL instance, and Harbor and GitLab each use their own Redis instance. Do not share an instance between products. The resources of each instance are counted in the row of its product in [Sizing Basis](#sizing-basis).

| Product | PostgreSQL | Redis |
| --- | --- | --- |
| Harbor | Own high availability instance, 3 nodes. Harbor 2.14 supports PostgreSQL 15.x and 16.x. | Own Sentinel instance: 1 master, 1 replica, 3 Sentinels. Redis 7.x is recommended. Redis Cluster mode is not supported. |
| GitLab | Own high availability instance, 3 nodes. GitLab 18.z supports PostgreSQL 16 and 17. | Own Sentinel instance: 1 master, 1 replica, 3 Sentinels. Redis 7.2 or later is required. Redis Cluster mode is not supported. |
| SonarQube | Own high availability instance, 3 nodes. SonarQube supports PostgreSQL 13 to 17. | Not used. |
| Nexus | Not used. | Not used. |

Create the instances with the platform PostgreSQL and Redis operators, then give each product its connection credentials:

## Sizing Basis \{#sizing-basis}

This section shows how the figures above are derived. All CPU and memory values are limits, and requests are assumed to equal limits. Node specifications are rounded up to common machine sizes: 4, 8, 12, 16, 24, or 32 cores and 8, 16, 24, 32, 48, or 64 GiB of memory. Data disks are rounded up to 100, 200, 300, 500, 1000, or 2000 GiB.

### devops Pool

| Product | Component | CPU | Memory (GiB) | Source |
| --- | --- | --- | --- | --- |
| Harbor | Harbor components | 8 | 16 | `Harbor Object Storage` template (8 cores, 16 Gi), which also matches the high availability minimum on the same page |
| | PostgreSQL: 3 × (2 + exporter 0.5) cores, 3 × (4 + exporter 0.5) GiB | 7.5 | 13.5 | High availability example in the PostgreSQL documentation |
| | Redis Sentinel: 2 × (1 + exporter 0.1) cores, 2 × (2 + exporter 0.375) GiB, plus 3 Sentinels × 0.1 cores / 0.125 GiB | 2.5 | 5.125 | Sentinel example in the Redis documentation |
| | **Subtotal** | **18** | **34.625** | |
| GitLab | GitLab components | 18 | 22 | High availability minimum on the GitLab deployment page (18 cores, 22 Gi). The limits of the high availability YAML example with one Gitaly add up to 16 cores and 20 GiB |
| | PostgreSQL, same shape as Harbor | 7.5 | 13.5 | PostgreSQL documentation |
| | Redis Sentinel, same shape as Harbor | 2.5 | 5.125 | Redis documentation |
| | **Subtotal** | **28** | **40.625** | |
| SonarQube | SonarQube | 8 | 16 | `Production Template` (8 cores, 16 Gi) |
| | PostgreSQL, same shape as Harbor | 7.5 | 13.5 | PostgreSQL documentation |
| | **Subtotal** | **15.5** | **29.5** | |
| Nexus | Nexus | 4 | 8 | `Production Template` (4 cores, 8 Gi) |
| Alauda DevOps Pipelines | Tekton components | 4 | 4 | Planning allowance. The documentation gives example values only for some controllers (about 2.7 cores and 2.25 GiB in total) |
| **Total** | | **69.5** | **116.75** | |

With 4 nodes of 32 cores and 64 GiB, the pool has 128 cores and 256 GiB. When one node is unavailable, the remaining 96 cores and 192 GiB still hold the total, with room left for DaemonSets and node reservations.

The total does not include:

- PipelineRun and TaskRun pods.
- The GitLab `migrations` Job (1 core, 1 GiB), which runs during installation and upgrade.
- The three Nexus logging containers and the operator pods, whose resources are not documented.
- The optional Tekton Results component, which needs its own external PostgreSQL database.

### storage Pool

Ceph component recommendations: MON 2 cores / 3 GiB, MGR 3 cores / 4 GiB, RGW 2 cores / 4 GiB, OSD 4 cores / 8 GiB. A cluster typically runs 3 MON, 2 MGR, and 2 RGW when object storage is used. With one MON, one MGR, one RGW, and one OSD on a node, the node needs 11 cores and 19 GiB, rounded up to 12 cores and 24 GiB.

OSD capacity is planned from the volumes in the following table. Volume sizes follow the examples and minimums in the product documentation. The object storage size is a planning assumption; replace it with the expected image and upload volume.

| Data | Storage | Volumes × size | Usable capacity (GiB) |
| --- | --- | --- | --- |
| PostgreSQL: Harbor, GitLab, SonarQube | RBD | 3 instances × 3 nodes × 50 GiB | 450 |
| Redis: Harbor, GitLab | RBD | 2 instances × 2 data nodes × 2 GiB | 8 |
| GitLab Gitaly | RBD | 1 × 20 GiB | 20 |
| SonarQube data | RBD | 1 × 10 GiB | 10 |
| Nexus data | RBD | 1 × 200 GiB | 200 |
| Harbor registry and GitLab uploads | RGW | Planning assumption | 500 |
| **Total** | | | **1188** |

Ceph keeps 3 replicas by default. With 3 storage nodes and one OSD on each node, every OSD holds one full replica, so each OSD needs the total usable capacity. Ceph raises the near-full alert at 80% utilization, so each OSD needs at least 1188 / 0.8 ≈ 1485 GiB, rounded up to 2000 GiB. Recalculate with the expected sizes of the repositories, artifacts, and images.

### control-plane and infra Pools

- control-plane: the workload cluster evaluation lists 4 cores and 16 GB for clusters with up to 24 worker nodes. The DevOps cluster has 10 worker nodes. 8 cores and 32 GiB leaves headroom for the recommended utilization of about 60% or less, and matches the control-plane nodes of the workload clusters.
- infra: 16 cores and 48 GiB, the same as the infra nodes of the workload clusters. The smallest scale in the monitoring capacity planning is 10 worker nodes and 500 pods; the DevOps cluster has 10 worker nodes.
