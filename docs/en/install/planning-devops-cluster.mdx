# Planning Harbor and the DevOps Tools

Use this page to plan the additional machines for Harbor and the other Alauda DevOps tools in an Alauda Container Platform (ACP) 4.5 multi-cluster installation on Alauda OS. It adds to the `global` and workload cluster sizes of the ACP installation planning.

A multi-cluster platform uses one central image registry for application images. If the customer already has one, use it and skip this page. Otherwise, use Harbor in one of two ways:

| Case | When | What to add |
| --- | --- | --- |
| [Case 1: Harbor on the global Cluster](#harbor-on-global) | Only a central registry is needed | A harbor pool and a storage pool on the `global` cluster |
| [Case 2: Dedicated DevOps Cluster](#devops-cluster) | GitLab, pipelines, SonarQube, or Nexus are also needed | A new workload cluster that runs all the tools, including Harbor |

## Resource Requirements

The tables give the **minimum recommended size of each node**. Physical servers are usually larger; select servers that are at least this size. After the installation, scale up according to the actual utilization.

In both cases, the tools keep their data on Ceph, on dedicated storage nodes in the same cluster. Ceph needs at least 3 storage nodes, each with a dedicated raw disk. Without them, this plan cannot be delivered.

### Case 1: Harbor on the global Cluster \{#harbor-on-global}

ACP recommends running only platform components on the `global` cluster of a multi-cluster platform. A central Harbor is an exception: it serves every cluster of the platform, and running it on the `global` cluster avoids a separate cluster for the registry alone. It runs on its own node pools.

#### Machines

| Node pool | Nodes | CPU | Memory | Runs |
| --- | ---: | --- | --- | --- |
| harbor | 3 | 12 cores | 24 GiB | Harbor, its PostgreSQL and Redis, Envoy Gateway |
| storage | 3 (4 on Bare Metal) | 8 cores | 24 GiB | Ceph |

In total: 6 nodes, 60 cores, and 144 GiB of memory. On Bare Metal: 7 nodes, 68 cores, and 168 GiB.

- On Bare Metal, use 4 storage nodes. A replacement server can take a long time to arrive. With 3 nodes, Ceph would run degraded on 2 nodes for that time, and maintenance and upgrades would be blocked.
- With `global` disaster recovery, prepare these pools on the primary only. Harbor disaster recovery is optional; if it is required, prepare the same pools on the standby as well.

#### Disks

Sizes are per node, in GB. For what each disk holds, see [Disk Configuration](https://docs.alauda.io/container_platform/4.5/configure/scalability/disk_configuration.html).

| Disk | harbor | storage |
| --- | ---: | ---: |
| **On Huawei DCS, Huawei Cloud Stack, or VMware vSphere** | | |
| System disk | 100 | 100 |
| `/var/lib/containerd` | 150 | 150 |
| `/var/lib/kubelet` | 200 | 200 |
| `/var/cpaas` (persistent) | 50 | 50 |
| **On Bare Metal** | | |
| System disk, minimum / recommended | 512 / 512 | 512 / 512 |
| **On all providers** | | |
| Raw disk for the Ceph OSD (SSD) | — | 1 TB |
| Persistent disk for `/var/lib/rook` | — | 100 |

- `/var/lib/kubelet` is 200 GB because these are `global` cluster nodes.
- The harbor nodes need no data disk. All Harbor data is on Ceph or on the customer's object storage.
- The OSD size assumes 500 GB of image layers. If the image layers use the customer's object storage, 512 GB is enough. See [OSD Capacity](#osd-capacity).

### Case 2: Dedicated DevOps Cluster \{#devops-cluster}

All DevOps tools, including Harbor, run in a workload cluster of their own.

#### Machines

| Node pool | Nodes | CPU | Memory | Runs |
| --- | ---: | --- | --- | --- |
| control-plane | 3 | 4 cores | 16 GiB | Control plane and platform components |
| infra | 3 | 16 cores | 48 GiB | Monitoring, logging, Envoy Gateway |
| devops | 4 | 32 cores | 64 GiB | The DevOps tools and their PostgreSQL and Redis; light builds |
| storage | 3 (4 on Bare Metal) | 8 cores | 24 GiB | Ceph |
| pipeline | 3 to 6 | 4 or 8 cores | 16 or 32 GiB | Builds, only for 3 or more concurrent PipelineRuns; see [Pipeline Pool](#pipeline-pool) |

In total, without the pipeline pool: 13 nodes, 212 cores, and 520 GiB of memory. On Bare Metal: 14 nodes, 220 cores, and 544 GiB.

#### Disks

Sizes are per node, in GB. For what each disk holds, see [Disk Configuration](https://docs.alauda.io/container_platform/4.5/configure/scalability/disk_configuration.html).

| Disk | control-plane | infra | devops | storage | pipeline |
| --- | ---: | ---: | ---: | ---: | ---: |
| **On Huawei DCS, Huawei Cloud Stack, or VMware vSphere** | | | | | |
| System disk | 100 | 100 | 100 | 100 | 100 |
| `/var/lib/etcd` | 20 | — | — | — | — |
| `/var/lib/containerd` | 150 | 150 | 150 | 150 | 150 |
| `/var/lib/kubelet` | 100 | 100 | 100 | 100 | 100 |
| `/var/cpaas` (persistent) | 100 | 200 | 50 | 50 | 50 |
| **On Bare Metal** | | | | | |
| System disk, minimum / recommended | 512 / 512 | 512 / 1 TB | 512 / 512 | 512 / 512 | 512 / 512 |
| **On all providers** | | | | | |
| Raw disk for TopoLVM | — | 1 TB | — | — | — |
| Raw disk for the Ceph OSD (SSD) | — | — | — | 2 TB | — |
| Persistent disk for `/var/lib/rook` | — | — | — | 100 | — |

- The devops nodes need no data disk. All tool data is on Ceph.
- The OSD size assumes 500 GB of object storage. See [OSD Capacity](#osd-capacity).
- If builds use `emptyDir` workspaces or caches, enlarge `/var/lib/kubelet` on the pipeline nodes.

#### Pipeline Pool \{#pipeline-pool}

A separate pipeline pool is not needed by default. Size it by the number of PipelineRuns that run at the same time at peak, not by the number of pipelines.

| Peak concurrent PipelineRuns | Where builds run |
| --- | --- |
| 1 to 2 | On the devops nodes. No pipeline pool. |
| 3 to 5 | Pipeline pool: 4 nodes, 8 cores, 32 GiB |
| 6 to 10 | Pipeline pool: 6 nodes, 8 cores, 32 GiB |
| More than 10 | Pipeline pool sized with the formula in [Pipeline Sizing](#pipeline-sizing) |

- When builds run on the devops nodes, limit the build namespaces with a `ResourceQuota` of 6 cores and 24 GiB, so that builds cannot starve the tools.
- Do not run builds on the control-plane, infra, or storage nodes.

## Sizing Basis \{#sizing-basis}

CPU and memory are limits, and requests are assumed to equal limits. Node sizes are rounded up to common sizes: 4, 8, 12, 16, 24, or 32 cores and 8, 16, 24, 32, 48, or 64 GiB.

### Tool Resources

Resources are given per replica. Multiply by the number of replicas for the total.

| Tool | Component | CPU per replica | Memory per replica | Replicas |
| --- | --- | ---: | ---: | ---: |
| Harbor | Harbor components | 2 cores | 4 GiB | 3 |
| | PostgreSQL | 1 core | 2 GiB | 3 |
| | Redis data node | 1 core | 2 GiB | 2 |
| | Redis Sentinel | 0.1 cores | 0.125 GiB | 3 |
| GitLab | GitLab components | 8 cores | 9 GiB | 3 |
| | PostgreSQL | 1 core | 2 GiB | 3 |
| | Redis data node | 1 core | 2 GiB | 2 |
| | Redis Sentinel | 0.1 cores | 0.125 GiB | 3 |
| SonarQube | SonarQube | 8 cores | 16 GiB | 1 |
| | PostgreSQL | 1 core | 2 GiB | 3 |
| Nexus | Nexus, with its 3 logging containers | 6.6 cores | 13.5 GiB | 1 |
| Alauda DevOps Pipelines | Tekton components | 4 cores | 4 GiB | 1 |
| Envoy Gateway (Case 1 only) | Controller | 1 core | 1 GiB | 1 |
| | `envoy-proxy` | 2 cores | 2 GiB | 2 |

- **Harbor and GitLab components** are planned as a share per node across 3 nodes for the high availability form. The share covers all their components, which run 1 or 2 replicas each. Scale up when the load grows.
- **PostgreSQL** runs as a high availability instance of 3 nodes for each tool. One node is the primary and serves all connections; the other nodes are standbys. Scale up the instance when the load grows. This is below the 2 cores and 4 GB per node that the PostgreSQL documentation recommends as a minimum.
- **Redis** runs in Sentinel mode: 1 master, 1 replica, and 3 Sentinels.
- **SonarQube** uses its `Production Template` (8 cores, 16 Gi).
- **Nexus** uses its `Production Template`. The 4 cores and 8 Gi in the template description are requests; the limits are 6 cores and 12 Gi, plus 0.2 cores and 512 Mi for each logging container.
- **Tekton** is a planning allowance. Its components request about 3.4 cores and 3.5 GiB, including Triggers, Results, and Artifact Hub.
- **Envoy Gateway**: the controller value is its default limit. The `envoy-proxy` value is a planning allowance.
- **Not counted**: the metrics exporters of PostgreSQL and Redis (about 5 cores and 6 GiB in Case 2), the GitLab `migrations` Job, and the operator Pods. The headroom of the pools covers them.

### Node Pool Check

Each pool must still hold its workload when one node is unavailable.

| Node pool | Workload | Nodes × size | Remaining with one node down | Utilization (CPU / memory) |
| --- | --- | --- | --- | --- |
| harbor | 16.3 cores, 27.4 GiB | 3 × 12 cores / 24 GiB | 24 cores, 48 GiB | 68% / 57% |
| devops | 62.2 cores, 99.3 GiB | 4 × 32 cores / 64 GiB | 96 cores, 192 GiB | 65% / 52% |
| devops, with light builds | 68.2 cores, 123.3 GiB | 4 × 32 cores / 64 GiB | 96 cores, 192 GiB | 71% / 64% |

- harbor: Harbor with its PostgreSQL and Redis, plus Envoy Gateway. With 8 cores per node, 2 nodes would not hold it.
- devops: all tools. With 24 cores per node, CPU utilization would reach about 86%.
- Builds of 3 to 5 concurrent PipelineRuns on the devops nodes would raise memory utilization to about 89%, so they need the pipeline pool.
- storage: one OSD and the block and object services per node. The small three-node baseline of the Ceph planning page reserves about 20 CPUs and 40 GiB for such a cluster; 3 nodes of 8 cores and 24 GiB cover it. See [Aggregate Cluster Planning Budget](https://docs.alauda.io/container_platform/4.5/storage/storagesystem_ceph/planning.html#aggregate-cluster-planning-budget).
- control-plane: the DevOps cluster has fewer than 24 worker nodes, so it uses the 24-worker tier of [Evaluating Resources for Workload Cluster](https://docs.alauda.io/container_platform/4.5/configure/scalability/evaluating_workload.html).
- infra: the same components and tiers as the infra nodes of a workload cluster with about 20 worker nodes.

### Pipeline Sizing \{#pipeline-sizing}

One PipelineRun peaks at the requests of the Tasks that run at the same time, in the `java-image-build-scan-deploy` and `python-image-build-scan-deploy` pipelines of the Alauda catalog:

- Java: about 1.5 cores and 1.81 GiB.
- Python: about 2.3 cores and 2.32 GiB. The tiers use this value.

The tiers assume that about 75% of each node is available to builds, and keep one node in reserve. For `J` Java and `P` Python PipelineRuns at peak, on nodes of 8 cores and 32 GiB:

```text
Rcpu  = 1.5 J + 2.3 P          (cores)
Rmem  = 1.81 J + 2.32 P        (GiB)
Nodes = max(3, 1 + ceil(Rcpu / 6), 1 + ceil(Rmem / 24))
```

Real builds can exceed the Task requests. After the installation, watch pending TaskRuns, node utilization, OOM kills, and CPU throttling over at least two busy periods, then adjust.

### OSD Capacity \{#osd-capacity}

Volume sizes follow the default or example sizes in the product documentation. Replace the object storage row with the expected volume: image layers, PostgreSQL backups, and in Case 2 also GitLab objects. 500 GB is the minimum used here.

| Data | Storage | Volumes × size (GB) | Case 1 (GB) | Case 2 (GB) |
| --- | --- | --- | ---: | ---: |
| PostgreSQL | RBD | 3 × 50 per instance | 150 | 450 |
| Redis | RBD | 2 × 2 per instance | 4 | 8 |
| GitLab Gitaly | RBD | 1 × 50 | — | 50 |
| SonarQube data | RBD | 1 × 30 | — | 30 |
| Nexus data | RBD | 1 × 200 | — | 200 |
| Object storage | RGW | Expected volume, at least 500 | 500 | 500 |
| **Total** | | | **654** | **1238** |

Ceph keeps 3 replicas, and each storage node holds one OSD. After a node fails, Ceph restores 3 replicas on the remaining nodes, so each OSD must hold one full copy. Ceph raises the near-full alert at 80% utilization. Each OSD therefore needs:

- Case 1: 654 / 0.8 ≈ 818 GB, rounded up to 1 TB. With the image layers on the customer's object storage: 154 / 0.8 ≈ 193 GB, rounded up to 512 GB.
- Case 2: 1238 / 0.8 ≈ 1548 GB, rounded up to 2 TB.

## Solution Selection \{#tools}

In Case 1, only the Harbor rows apply.

### Deployment Form

| Tool | Operator in OperatorHub | Deployment form |
| --- | --- | --- |
| Harbor | `Alauda Toolchain Enterprise Registry E1` | High availability; at least 2 replicas of portal, core, registry, and jobservice |
| GitLab | `Alauda Toolchain Code Repository E1` | 2 replicas of webservice, Sidekiq, and gitlab-shell; a single Gitaly, not Gitaly Cluster |
| Alauda DevOps Pipelines | `Alauda Container Platform Pipelines` | Operator-managed Tekton components |
| SonarQube | `Alauda Build of SonarQube` | `Production Template`, single instance |
| Nexus | `Alauda Build of Nexus` | `Production Template`, single instance |

### Data and Middleware

Block data is on Ceph block storage (RBD). Object data is on Ceph object storage (RGW), or on the customer's S3-compatible storage. Each tool uses its own PostgreSQL and Redis instances; do not share an instance between tools.

| Tool | On Ceph RBD | On object storage | PostgreSQL | Redis |
| --- | --- | --- | --- | --- |
| Harbor | PostgreSQL, Redis | Image layers, PostgreSQL backups | 15.x or 16.x | 7.x, Sentinel |
| GitLab | Gitaly, PostgreSQL, Redis | Uploads, CI artifacts, LFS, packages, PostgreSQL backups | 16 or 17 | 7.2 or later, Sentinel |
| SonarQube | Data directory, PostgreSQL | PostgreSQL backups | 13 to 17 | — |
| Nexus | `/nexus-data` | — | — | — |

- Harbor keeps its job logs in its database, and its Trivy vulnerability database in an `emptyDir`.
- Harbor and GitLab do not support Redis Cluster mode.

## Deployment Notes \{#deployment-notes}

### Network

- **Case 1**: install Envoy Gateway on the `global` cluster and place `envoy-proxy` on the harbor nodes. Reserve one VIP for the Harbor gateway.
- **Case 2**: reserve two VIPs, one for the control plane endpoint and one for the gateway that serves Harbor and GitLab.
- The gateway VIP can come from the enterprise load balancer, or from MetalLB. On Huawei Cloud Stack, run `envoy-proxy` with the host network behind the HCS ELB.

See [Tasks for Envoy Gateway](https://docs.alauda.io/container_platform/4.5/networking/how_to/tasks_for_envoy_gateway.html).

### Node Pools

- **Case 1**: give each pool a role label. Schedule Harbor and its PostgreSQL and Redis to the harbor nodes with node selectors. Taint the storage pool.
- **Case 2**: taint the infra, storage, and pipeline pools, and leave the devops pool untainted. The tools then run on the devops nodes, the only nodes without a taint.
- To send builds to the pipeline pool, set `nodeSelector` and `tolerations` in `spec.pipeline.default-pod-template` of the `TektonConfig`. See <ExternalSiteLink name="alauda-devops-pipelines" href="/configure/pod_template_guide.html" children="Pod Template Configuration Guide" />.

### Harbor

The built-in templates do not combine object storage with Envoy Gateway, so deploy Harbor from YAML:

- Expose it with `expose.type: route`, as in Option B of <ExternalSiteLink name="alauda-build-of-harbor" href="/howto/11_expose_with_envoy_gateway.html" children="Expose Harbor with Envoy Gateway" />.
- Store the image layers on object storage, as in <ExternalSiteLink name="alauda-build-of-harbor" href="/install/03_harbor_deploy.html#storage-yaml-snippets" children="Using Object Storage as the Registry Storage Backend" />.
- Store the job logs in the database, as in <ExternalSiteLink name="alauda-build-of-harbor" href="/howto/07_configure_job_log_storage.html#store-job-log-to-db" children="Configure Job Log Storage" />.
- Under `resources`, use the keys `requests` and `limits`.

For disaster recovery, see <ExternalSiteLink name="alauda-build-of-harbor" href="/howto/10_disaster_recovery.html" children="Harbor Disaster Recovery" />. `global` cluster disaster recovery does not synchronize Harbor data.

### GitLab

- Do not use the `GitLab High Availability` template: it always enables Gitaly Cluster and a `ReadWriteMany` attachment volume. Deploy from YAML with `global.praefect.enabled: false`.
- Object storage is required. Without it, avatars, attachments, and CI artifacts stay inside each Pod and are lost when the Pod restarts.
  - Configure the connection in `global.appConfig.object_store.connection`.
  - Create the buckets `gitlab-uploads`, `gitlab-artifacts`, `git-lfs`, and `gitlab-packages` in advance.
  - Keep `global.uploads.persistence.enabled: true`, and leave its storage class empty.
- For production, the GitLab deployment page recommends read IOPS ≥ 8,000 and write IOPS ≥ 2,000 for Gitaly. Validate the Ceph RBD performance on the delivered hardware.

### Namespace Security

- SonarQube: use the `Privileged` Pod Security level. SonarQube sets kernel parameters with a privileged init container.
- GitLab: do not use the `Restricted` level.

### Single Instances on Ceph RBD

GitLab Gitaly, SonarQube, and Nexus run one Pod each, on a `ReadWriteOnce` volume. If the node fails, Kubernetes does not move the Pod by itself, and the tool is unavailable until you do one of the following:

- Delete the Pod with `--force`.
- Add the `node.kubernetes.io/out-of-service` taint to the failed node.

The Pod then starts on another node. See [Non-Graceful Node Shutdown](https://kubernetes.io/docs/concepts/cluster-administration/node-shutdown/).

### Storage

- Do not place databases on CephFS. The plan does not use CephFS, so no MDS runs.
- Do not use remote-mounted file storage for SonarQube data.
- PostgreSQL and Redis replicate their own data, and Ceph RBD keeps 3 replicas, so each database is stored 9 times. The plan accepts this to keep one storage system for all tool data; the OSD capacity counts it.
