# Planning Harbor and the DevOps Tools

Use this page to plan the machines, disks, storage, and middleware for Harbor and the other Alauda DevOps tools in an Alauda Container Platform (ACP) 4.5 multi-cluster installation on Alauda OS. It adds to the `global` and workload cluster sizes of the ACP installation planning; it does not repeat them.

A multi-cluster platform uses one central image registry for application images. If the customer already has a central registry, use it and skip this page. Otherwise, use Harbor in one of two ways:

| Case | When it applies | What to add | Plan |
| --- | --- | --- | --- |
| 1. Harbor only | The customer needs a central registry, but no other DevOps tools | A harbor node pool and a storage node pool on the `global` cluster | [Case 1: Harbor on the global Cluster](#harbor-on-global) |
| 2. Harbor and other DevOps tools | The customer also needs GitLab, pipelines, SonarQube, or Nexus | A dedicated DevOps cluster, which also runs Harbor | [Case 2: Dedicated DevOps Cluster](#devops-cluster) |

In both cases, the tools keep their data on Ceph distributed storage that runs on dedicated storage nodes in the same cluster, and each tool uses its own PostgreSQL and Redis instances in that cluster.

## Additional Machines at a Glance \{#at-a-glance}

The values are the **minimum recommended size of each node**. Physical servers are usually larger; select servers that are at least this size. CPU and memory assume that requests equal limits.

**Case 1**, added to the `global` cluster. With `global` disaster recovery, prepare it for the primary only; see [Disaster Recovery](#harbor-dr).

| Node pool | Nodes | CPU | Memory | Purpose |
| --- | ---: | --- | --- | --- |
| harbor | 3 | 16 cores | 32 GiB | Harbor, its PostgreSQL and Redis instances, and the Envoy Gateway proxies that expose Harbor |
| storage | 3 on Huawei DCS, Huawei Cloud Stack, or VMware vSphere; 4 on Bare Metal | 8 cores | 24 GiB | Ceph |

In total: 6 nodes, 72 cores, and 168 GiB of memory; on Bare Metal, 7 nodes, 80 cores, and 192 GiB.

**Case 2**, a new workload cluster:

| Node pool | Nodes | CPU | Memory | Purpose |
| --- | ---: | --- | --- | --- |
| control-plane | 3 | 4 cores | 16 GiB | Control plane and platform components |
| infra | 3 | 16 cores | 48 GiB | Monitoring, logging, and the gateway (Envoy Gateway) of this cluster |
| devops | 4 | 32 cores | 64 GiB | The DevOps tools and their PostgreSQL and Redis instances |
| storage | 3 on Huawei DCS, Huawei Cloud Stack, or VMware vSphere; 4 on Bare Metal | 8 cores | 24 GiB | Ceph |
| pipeline | 3 to 6, by build load | 4 or 8 cores | 16 or 32 GiB | PipelineRun and TaskRun Pods; see [Pipeline Pool](#pipeline-pool) |

Without the pipeline pool: 13 nodes, 212 cores, and 520 GiB of memory; on Bare Metal, 14 nodes, 220 cores, and 544 GiB.

For the disks of each pool, see the Disks section of each case. The sizes follow the product capacity tiers in [Sizing Basis](#sizing-basis). After the installation, scale up according to the actual utilization.

## Case 1: Harbor on the global Cluster \{#harbor-on-global}

ACP recommends running only platform components on the `global` cluster of a multi-cluster platform. A central Harbor is an exception: it serves every cluster of the platform, and running it on the `global` cluster avoids a separate cluster for the registry alone. Run it on its own node pools so that it does not compete with the platform components.

### Machines

| Node pool | Nodes | CPU | Memory | Purpose |
| --- | ---: | --- | --- | --- |
| harbor | 3 | 16 cores | 32 GiB | Harbor, its PostgreSQL and Redis instances, and the Envoy Gateway proxies that expose Harbor |
| storage | 3 on Huawei DCS, Huawei Cloud Stack, or VMware vSphere; 4 on Bare Metal | 8 cores | 24 GiB | Ceph block storage (RBD) for PostgreSQL and Redis, and Ceph object storage (RGW) for the image layers. Spread the nodes across failure domains. |

- With one harbor node unavailable, the other 2 nodes still hold all Harbor Pods.
- On Bare Metal, use 4 storage nodes. A replacement for a failed server can take a long time to arrive; with 3 nodes, Ceph runs degraded on 2 nodes for that time, and maintenance and upgrades are blocked. With 4 nodes, Ceph can restore all 3 replicas on the remaining nodes.

### Disks

Sizes are per node, in GB. The nodes are `global` cluster nodes, so `/var/lib/kubelet` is 200 GB. For what each disk holds, see [Disk Configuration](https://docs.alauda.io/container_platform/4.5/configure/scalability/disk_configuration.html).

| `/var/lib/containerd` | 150 | 150 |
| `/var/lib/kubelet` | 200 | 200 |
| `/var/cpaas` (persistent) | 50 | 50 |
| **On Bare Metal** | | |
| System disk, minimum / recommended | 512 / 512 | 512 / 512 |
| **On all providers** | | |
| Raw disk for TopoLVM | — | — |
| Raw disk for the Ceph OSD (SSD) | — | 1 TB; 512 if the image layers use the customer's object storage |
| Persistent disk for `/var/lib/rook` | — | 100 |

The harbor nodes need no data disk: all Harbor data is on Ceph or on the customer's object storage. The OSD size assumes 500 GB of image layers; replace it with the expected image volume; see [OSD Capacity](#osd-capacity).

### Network and Node Pools

- Expose Harbor through Envoy Gateway (Gateway API). Install Envoy Gateway on the `global` cluster and place `envoy-proxy` on the harbor nodes. For the gateway VIP, allocate one on the enterprise load balancer, or use MetalLB; on Huawei Cloud Stack, run `envoy-proxy` with the host network behind the HCS ELB. See [Tasks for Envoy Gateway](https://docs.alauda.io/container_platform/4.5/networking/how_to/tasks_for_envoy_gateway.html).
- Declare a role label on each pool, and schedule Harbor and its PostgreSQL and Redis instances to the harbor nodes with node selectors. Give the storage pool its own role label and taint.

### Disaster Recovery \{#harbor-dr}

Harbor disaster recovery is optional. If it is required, prepare the same harbor and storage node pools on the standby `global` cluster, and set up <ExternalSiteLink name="alauda-build-of-harbor" href="/howto/10_disaster_recovery.html" children="Harbor disaster recovery" />; `global` cluster disaster recovery does not synchronize Harbor data.

### Pipeline Pool \{#pipeline-pool}

Size the pipeline pool by the number of PipelineRuns that run at the same time at peak, not by the number of pipelines that exist.

| Peak concurrent PipelineRuns | pipeline nodes |
| --- | --- |
| 1 to 2 (light) | 3 × 4 cores / 16 GiB |
| 3 to 5 (medium) | 4 × 8 cores / 32 GiB |
| 6 to 10 (heavy) | 6 × 8 cores / 32 GiB |

For more than 10, see the formula in [Sizing Basis](#pipeline-sizing).

If no additional machines are available:

- **Light load** can run on the devops nodes. With one devops node unavailable, about 24 cores and 70 GiB remain after the tools, which covers the light tier. Cap the build namespaces with a `ResourceQuota` of 6 cores and 24 GiB, so that builds cannot starve GitLab, Harbor, or the databases.
- **Medium and heavy load** need the pipeline pool. Their peak exceeds what the devops nodes have left with one node unavailable.
- Do not run builds on the control-plane, infra, or storage nodes.

Taint the pipeline pool, and send the PipelineRun and TaskRun Pods to it with the default Pod template of Tekton: set `nodeSelector` and `tolerations` in `spec.pipeline.default-pod-template` of the `TektonConfig`. See <ExternalSiteLink name="alauda-devops-pipelines" href="/configure/pod_template_guide.html" children="Pod Template Configuration Guide" />.

### Network and Node Pools

- Reserve two VIPs for the DevOps cluster: the control plane endpoint, and the gateway VIP for Harbor and GitLab. Both can come from the enterprise load balancer. The choices are the same as for any workload cluster.
- Give the infra, storage, and pipeline pools their own role labels and taints, and leave the devops pool without a taint. The tools and their PostgreSQL and Redis instances then run on the devops nodes, the only nodes without a taint.

## Deployment Notes for Both Cases \{#deployment-notes}

- **Harbor**: the built-in templates do not combine object storage with Envoy Gateway. Deploy from YAML. Set `expose.type: route` as in Option B of <ExternalSiteLink name="alauda-build-of-harbor" href="/howto/11_expose_with_envoy_gateway.html" children="Expose Harbor with Envoy Gateway" />, store the image layers on object storage as in <ExternalSiteLink name="alauda-build-of-harbor" href="/install/03_harbor_deploy.html#storage-yaml-snippets" children="Using Object Storage as the Registry Storage Backend" />, and store the job logs in the database as in <ExternalSiteLink name="alauda-build-of-harbor" href="/howto/07_configure_job_log_storage.html#store-job-log-to-db" children="Configure Job Log Storage" />. In `resources`, use the keys `requests` and `limits`.
- **GitLab**: the `GitLab High Availability` template always enables Gitaly Cluster and a `ReadWriteMany` attachment volume, so do not use it. Deploy from YAML with `global.praefect.enabled: false`.
- **GitLab object storage is required.** Without it, avatars, attachments, and CI artifacts are kept inside each Pod and are lost when the Pod restarts. Configure the connection in `global.appConfig.object_store.connection`, and create the buckets `gitlab-uploads`, `gitlab-artifacts`, `git-lfs`, and `gitlab-packages` in advance. Keep `global.uploads.persistence.enabled: true` and leave its storage class empty.
- **Namespace security**: the SonarQube namespace must use the `Privileged` Pod Security level, because SonarQube sets kernel parameters with a privileged init container. The GitLab namespace must not use the `Restricted` level.
- **Single instances on Ceph RBD**: GitLab Gitaly, SonarQube, and Nexus run one Pod each, on a `ReadWriteOnce` volume. If their node goes down, Kubernetes does not move the Pod to another node by itself. Delete the Pod with `--force`, or add the `node.kubernetes.io/out-of-service` taint to the failed node; the Pod then starts on another node. Until then, the tool is unavailable. See [Non-Graceful Node Shutdown](https://kubernetes.io/docs/concepts/cluster-administration/node-shutdown/).

## Storage

| Data | Storage | Notes |
| --- | --- | --- |
| PostgreSQL of Harbor, GitLab, and SonarQube | Ceph RBD | Do not place databases on CephFS. |
| Redis of Harbor and GitLab | Ceph RBD | RDB persistence enabled. |
| Harbor image layers | Ceph RGW, or the customer's S3-compatible storage | |
| Harbor job logs | Harbor database | |
| Harbor Trivy vulnerability database | `emptyDir` | After a Trivy Pod restarts, scans pause until the database is loaded again. |
| GitLab Gitaly (repositories) | Ceph RBD | The GitLab deployment page recommends block storage with read IOPS ≥ 8,000 and write IOPS ≥ 2,000 for production. Validate the Ceph RBD performance on the delivered hardware. |
| GitLab uploads, CI artifacts, LFS objects, and packages | Ceph RGW, or the customer's S3-compatible storage | Required; see [Deployment Notes](#deployment-notes). |
| SonarQube data directory | Ceph RBD | Do not use remote-mounted file storage for SonarQube data. |
| Nexus data (`/nexus-data`) | Ceph RBD | One volume for the single instance. |
| PostgreSQL backups | Ceph RGW, or the customer's S3-compatible storage | The PostgreSQL operator writes backups to S3-compatible storage. |

The plan does not use CephFS, so no MDS runs.

PostgreSQL and Redis replicate their own data, and Ceph RBD keeps 3 replicas of each volume, so every database is stored 9 times and each write waits for Ceph replication. The plan accepts this to keep one storage system for all tool data. The capacity table counts it.

:::warning
Ceph requires at least 3 storage nodes, each with a dedicated raw disk. If the environment cannot provide them, this plan cannot be delivered.
:::

## Sizing Basis \{#sizing-basis}

All CPU and memory values are limits, and requests are assumed to equal limits. Node sizes are rounded up to common machine sizes: 4, 8, 12, 16, 24, or 32 cores and 8, 16, 24, 32, 48, or 64 GiB of memory. Each pool is sized so that the remaining nodes hold its workload when one node is unavailable.

### harbor Pool (Case 1)

Harbor with its PostgreSQL and Redis needs 18 cores and 34.625 GiB. The Envoy Gateway controller adds 1 core and 1 GiB (its default limits), and 2 `envoy-proxy` replicas are planned at 2 cores and 2 GiB each: in total, 23 cores and 39.625 GiB. With one of 3 nodes of 16 cores and 32 GiB unavailable, the remaining 32 cores and 64 GiB hold this at about 72% CPU and 62% memory. Nodes of 12 cores and 24 GiB would run at about 96% CPU.

### devops Pool (Case 2)

All tools need 72.1 cores and 122.25 GiB. With one of 4 nodes of 32 cores and 64 GiB unavailable, the remaining 96 cores and 192 GiB hold them at about 75% CPU and 64% memory, and about 24 cores and 70 GiB remain. That covers the light pipeline tier, but not the medium tier.

### Pipeline Pool (Case 2) \{#pipeline-sizing}

The peak of one PipelineRun is taken from the requests of the Tasks that run at the same time in the `java-image-build-scan-deploy` and `python-image-build-scan-deploy` pipelines of the Alauda catalog:

- Java: about 1.5 cores and 1.81 GiB, while the SonarQube scan and the image build run in parallel.
- Python: about 2.3 cores and 2.32 GiB, while the pre-build and the SonarQube scan run in parallel. The tiers use this value.

The tiers assume that about 75% of each node is available to TaskRun Pods, and keep one node in reserve for a failure or maintenance. For `J` Java and `P` Python PipelineRuns at peak, on nodes of 8 cores and 32 GiB:

```text
Rcpu = 1.5 J + 2.3 P          (cores)
Rmem = 1.81 J + 2.32 P        (GiB)
Nodes = max(3, 1 + ceil(Rcpu / 6), 1 + ceil(Rmem / 24))
```

Tekton adds init containers and sidecars to each Pod, and real builds can exceed the Task requests. After the installation, watch the time that TaskRuns stay pending, node CPU and memory utilization, OOM kills, and throttling over at least two busy periods, then adjust the pool.

### storage Pool (Both Cases)

Each storage node runs one OSD and the block and object services. The small three-node baseline of the Ceph planning page reserves about 20 CPUs and 40 GiB for such a cluster; 3 nodes of 8 cores and 24 GiB cover it. See [Aggregate Cluster Planning Budget](https://docs.alauda.io/container_platform/4.5/storage/storagesystem_ceph/planning.html#aggregate-cluster-planning-budget).

### OSD Capacity \{#osd-capacity}

Volume sizes follow the default or example sizes in the product documentation. Replace the object storage row with the expected volume: image layers and their retention, PostgreSQL backups, and in Case 2 also GitLab objects. 500 GB is the minimum used here.

| Data | Storage | Volumes × size | Case 1 (GB) | Case 2 (GB) |
| --- | --- | --- | ---: | ---: |
| PostgreSQL | RBD | 3 nodes × 50 per instance: Harbor in Case 1; Harbor, GitLab, and SonarQube in Case 2 | 150 | 450 |
| Redis | RBD | 2 data nodes × 2 per instance: Harbor in Case 1; Harbor and GitLab in Case 2 | 4 | 8 |
| GitLab Gitaly | RBD | 1 × 50 | — | 50 |
| SonarQube data | RBD | 1 × 30 | — | 30 |
| Nexus data | RBD | 1 × 200 | — | 200 |
| Object storage | RGW | Expected volume, at least 500 | 500 | 500 |
| **Total usable capacity** | | | **654** | **1238** |

Ceph keeps 3 replicas, and each storage node holds one OSD. After a node fails, Ceph restores 3 replicas on the remaining nodes, so each OSD must be able to hold one full copy. Ceph raises the near-full alert at 80% utilization. Each OSD therefore needs:

- Case 1: 654 / 0.8 ≈ 818 GB, rounded up to 1 TB. With the image layers on the customer's object storage, 154 / 0.8 ≈ 193 GB, rounded up to 512 GB.
- Case 2: 1238 / 0.8 ≈ 1548 GB, rounded up to 2 TB.

### control-plane and infra Pools (Case 2)

- control-plane: the DevOps cluster has fewer than 24 worker nodes, so it uses the 24-worker tier of [Evaluating Resources for Workload Cluster](https://docs.alauda.io/container_platform/4.5/configure/scalability/evaluating_workload.html): 4 cores and 16 GiB.
- infra: the same components and tiers as the infra nodes of a workload cluster with about 20 worker nodes: monitoring, logging for 5,000 log entries per second with 7 days of retention, and Envoy Gateway.
